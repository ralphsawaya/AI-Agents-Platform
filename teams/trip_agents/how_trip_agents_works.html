A primer for engineers new to agentic AI

How the trip_agents system works

trip_agents is a small team of cooperating AI agents that turn natural-language travel requests — "plan a quiet weekend in Athens with a manual rental car" — into ranked flight, hotel, and car options, and lets the user book, modify, or cancel from chat. This page explains how it does that, top-down, assuming you've never built with LLM agents before.

If you're a software engineer You'll get the data flow, the orchestration code, and the shape of every message — enough to add a tool or extend a sub-agent confidently.
If you're a software architect You'll see the design trade-offs (plan-and-execute vs ReAct, JSON planning vs native tool calls, memory layers, two-database split) and where to draw the boundaries.

Sample request walking through the diagram: “Plan a full trip to Amsterdam — flight, hotel and car”

  1. 1User message arrives at /api/trip/{id}/threads/{tid}/messages via the chat box in trip_planner.html.
  2. 2The FastAPI route spawns a fresh Python subprocess running the orchestrator, passing the message via AGENT_ARGS.
  3. 3The plan node calls the LLM (call #1) with the user query, last 8 messages, and long-term preferences — and receives a JSON plan: { intent: "search", tool_calls: [...] }.
  4. 4Control moves to execute_tools, which will dispatch each call from the plan by name through the TOOL_REGISTRY.
  5. 5The three search tools fan out concurrently via ThreadPoolExecutor; the two read-only tools (get_user_preferences, get_reservation) read MongoDB directly without a sub-agent.
  6. 6Each search tool invokes its sub-agent (a tiny LangGraph): embed the query with Voyage AI, then run $vectorSearch against the matching MongoDB collection — top 3 hits per category.
  7. 7Merged search_results are handed to synthesize, which now has flights + hotels + cars to choose from.
  8. 8synthesize calls the LLM (call #2) to pick the best bundle and write a friendly reply; receives content + proposed_bundle.
  9. 9persist writes the assistant message to trip_chatPersistence and spawns a background thread that extracts new long-term preferences. Subprocess exits; the UI renders the chat reply on the right and the “Agent's Recommended Trip” card on the left.

01 The 30-second mental model

Why use AI agents for this at all, rather than a search form and some Python?

A travel request like "I want to fly Doha → Athens in March, a quiet riverside hotel with a bar, and a manual Kia" is hard to parse with regex. The hard parts aren't searching MongoDB — those are easy once you know the filters. The hard parts are:

  • Understanding intent. Does the user want a flight only? Or a full trip? Are they asking, or booking?
  • Deciding which searches to run. Skipping unrelated categories matters (don't search hotels when they only asked for a car).
  • Translating fuzzy descriptions ("quiet riverside hotel with a bar") into something the database can match — that's where vector search over embedded descriptions earns its keep.
  • Composing a coherent answer across the results: "here's a bundle, total €842, here's why I picked it."

The pattern is: an LLM decides what to do; deterministic Python decides how. The LLM is treated as a planner and writer; concrete tools (vector search, MongoDB reads, embedding calls) are plain Python functions. We never let the model invent inventory, and we never ask Python to interpret prose.

One-line summary. trip_agents is an LLM-driven dispatcher (the orchestrator) that calls three small specialist agents (flight, hotel, car), each of which runs an embedding + a MongoDB vector search, then a second LLM pass that turns the combined results into a friendly reply and a proposed bundle.

02 Agentic AI primer

Six terms you'll see throughout this document. Each is defined plainly, then anchored to trip_agents.

LLM (Large Language Model)
A network — Claude, GPT-4, Gemini, etc. — that, given a text prompt, returns more text. From your perspective, it's a stateless function: llm.invoke(prompt) → string. It can be wrong, slow, or temporarily unavailable, so you treat it like an unreliable remote service.
Here: shared/llm.py wraps Claude / Gemini / OpenAI / DeepSeek / Groq behind a single get_llm().invoke() with 3× retry and a 30 s timeout.
Agent
A loop around an LLM that lets it do things, not just talk. The minimum recipe is: (1) call the LLM with the user's request, (2) interpret its output, (3) optionally run code on the LLM's behalf, (4) feed the result back into the LLM for the next step. The "agency" is in step 3 — the model can affect the outside world.
Here: the orchestrator is an agent. It asks the LLM what to do, then runs the requested searches, then asks the LLM to write a reply over the results.
Tool / function-calling
A tool is a regular function exposed to the agent under a stable name (search_flights) with a documented input schema. The LLM doesn't run the function — it just emits "call search_flights with these arguments." Your code runs it, then hands the result back to the LLM.
Here: tools are plain Python in orchestrator/tools.py — no LangChain decorators. The plan prompt describes them; execute_tool_calls() dispatches them.
Orchestration
The control flow that sequences LLM calls and tool calls into a useful pipeline: "plan, then execute tools, then maybe retry, then summarise, then save." It's literally a state machine — and that's exactly what LangGraph encodes.
Here: a five-node LangGraph: plan → execute → (replan?) → synthesize → persist. Edges are deterministic Python predicates, not LLM decisions.
Memory
LLMs are stateless. Anything the agent should "remember" — the last few messages, the user's preferences — has to be re-injected into every prompt. Memory is a storage strategy plus a retrieval strategy, not a model feature.
Here: short-term = last 8 messages in trip_chatPersistence; long-term = up to 30 extracted preference facts in trip_longMemory, learned in a background thread.
Multi-agent system
When one "big" agent would become unwieldy, you split it into smaller agents that each own a narrow job, and have a parent agent (an orchestrator) coordinate them. Smaller surface area, smaller prompts, easier to reason about, and embarrassingly parallel.
Here: the orchestrator delegates each domain to its own LangGraph — agent_flight, agent_hotel, agent_car — and runs them concurrently when the plan asks for several.

Two more terms worth knowing

Embeddings & vector search
An embedding turns a piece of text into a fixed-length list of numbers (a vector) such that semantically similar texts have nearby vectors. Vector search finds documents whose embedding is closest to the query embedding — useful when the user's words don't match the database's words but the meaning does.
Here: Voyage AI's voyage-3-lite produces 512-dim vectors. MongoDB's $vectorSearch stage finds the closest 100 candidates, keeps the top 3, then exact-match filters (city, stars, fuel type…) narrow further.
Plan-and-Execute vs ReAct
ReAct is the loop most beginner tutorials show: thought → tool → observation → thought → tool… One tool at a time, each step decided after seeing the previous result. Plan-and-Execute asks the model to produce a small JSON plan up front (which tools, with what arguments), Python runs it, then the model writes the answer. Fewer LLM round-trips, more deterministic execution.
Here: we use Plan-and-Execute. The plan is a JSON object the LLM returns once; Python runs all the requested searches (in parallel where possible); a separate "synthesize" LLM call writes the reply over the merged results.

03 System architecture

A layered view from the browser down to MongoDB. The whole thing is one Python process per chat turn — there is no long-running agent service.

Five layers — browser, REST API, orchestrator process, specialist sub-agents, MongoDB.

What runs where

LayerRoleTech
UITwo tabs: Trip Planner (chat + results) and ReservationsPlain HTML/JS in ui/tabs/
APIThreads, messages, suggestions, seed, memory, reservationsFastAPI route agent_platform/api/routes/trip.py
OrchestratorOne Python process spawned per chat turn; runs the LangGraphorchestrator/main.py + orchestrator/graph.py
Sub-agentsEmbed query → MongoDB vector search → top 3 hitsagent_flight, agent_hotel, agent_car
DataInventory, chat history, reservations, long-term memory, vector indexesMongoDB databases agent_platform + trip_data
Architectural choice — subprocess per turn. Each user message triggers a brand-new orchestrator process via the platform's executor; state is rehydrated from MongoDB on the way in and persisted on the way out. The trade-off: cold-start cost (LangGraph compilation, Mongo connection) in exchange for crash isolation, dead-simple deployment, and the ability to swap LLM provider per agent.

04 The plan-and-execute loop

The heart of the system: a five-node LangGraph in orchestrator/graph.py.

Solid path = search/replan. Dashed orange = empty results trigger a replan (capped at 2). Dashed red = pure chat skips tools.

Node by node

NodeReadsWritesWhat it does
plan user query, last 8 messages, long-term prefs intent, reply?, tool_calls[] LLM call. Returns a JSON plan: chat (no tools), search (which tools + args), or replan (relax filters).
execute_tools tool_calls[] tool_results[], search_results, tool_trace Pure Python. Dispatches each call via TOOL_REGISTRY; independent searches fan out in a ThreadPoolExecutor. Each search publishes partials to trip_search_progress so the UI can stream.
replan_bump — replan_count++ Only entered when all invoked search tools returned zero. Increments a counter, then routes back to plan with a "previous results were empty, relax filters" hint.
synthesize merged search results, prefs reply, proposed_bundle LLM call. Picks the best flight/hotel/car, writes a one-paragraph reply, and assembles a proposed_bundle with total cost. Heuristic fallback if the LLM fails.
persist full state trip_chatPersistence; spawns memory thread Saves the assistant message (with search results + bundle) to the chat thread, then fires a background thread that asks the LLM to extract any new preferences ("prefers business class").
Why this graph, not a free agent loop? ReAct-style "let the LLM decide every step" is great when steps are unknown ahead of time. Here, we know there are at most three searches, they're independent, and we never want the model running unbounded tool calls. Plan-and-Execute gives us one LLM decision point, parallel tool execution, and a deterministic finish — measurable, debuggable, cheap.

What the plan actually looks like

The plan node returns a JSON object like this:

// LLM output (parsed by shared/json_utils.extract_json)
{
  "intent": "search",
  "reply": null,
  "tool_calls": [
    { "tool": "get_user_preferences", "args": {} },
    { "tool": "search_flights",        "args": { "destination_city": "Amsterdam" } },
    { "tool": "search_hotels",         "args": { "city": "Amsterdam" } },
    { "tool": "search_cars",           "args": { "pickup_city": "Amsterdam" } }
  ]
}

That object is the entire interface between the planning LLM and the rest of the system. The plan prompt (shared/prompts/trip_planner_plan.txt) is a system message that documents the available tools and gives few-shot examples — no SDK-specific "function-calling" feature is used, so any provider works the same way.

05 Deep dive: the orchestrator

A LangGraph StateGraph over a typed dict; nodes are plain functions that take a state and return a partial update.

The state — one source of truth

Every node in the orchestrator graph reads and writes the same dictionary. LangGraph merges each node's returned partial into the running state, then routes to the next node based on conditional edges.

teams/trip_agents/orchestrator/state.py (excerpt)
class TripAgentState(TypedDict, total=False):
    # Inputs
    query:           str
    thread_id:       str
    chat_history:    list      # short-term memory (last 8 msgs)
    mode:            str       # chat | search | modify | ...
    reservation_id:  str
    reservation:     dict

    # Filled by plan node
    plan:            dict      # raw LLM JSON
    intent:          str       # chat | search | replan
    reply:           str

    # Filled by execute node
    tool_results:    list
    search_results:  dict      # {flights:[], hotels:[], cars:[]}
    tool_trace:      list

    # Filled by synthesize node
    proposed_bundle: dict | None

    # Control
    replan_count:    int

Wiring the graph

If you've never seen LangGraph: a StateGraph is a directed graph where nodes are functions and edges can be conditional (a router function inspects the state and returns the next node's name). Here's the orchestrator's wiring, lightly trimmed:

teams/trip_agents/orchestrator/graph.py
graph = StateGraph(TripAgentState)
graph.add_node("plan",        plan_node)
graph.add_node("execute",     execute_tools_node)
graph.add_node("replan_bump", replan_bump)
graph.add_node("synthesize",  synthesize_node)
graph.add_node("persist",     persist_and_learn)

graph.add_edge(START, "plan")
graph.add_conditional_edges("plan",    route_after_plan,    {"execute": "execute", "persist": "persist"})
graph.add_conditional_edges("execute", route_after_execute, {"replan": "replan_bump", "synthesize": "synthesize"})
graph.add_edge("replan_bump", "plan")
graph.add_edge("synthesize",  "persist")
graph.add_edge("persist",     END)

The two routers are tiny:

def route_after_plan(state):
    return "persist" if state["intent"] == "chat" else "execute"

def route_after_execute(state):
    search_tr = [tr for tr in state["tool_results"] if tr["tool"] in SEARCH_TOOLS]
    empty     = search_tr and all(tr["count"] == 0 for tr in search_tr)
    if empty and state["replan_count"] < MAX_REPLAN:
        return "replan"
    return "synthesize"

How tools are exposed

Notice there's no @tool decorator and no provider-specific "function definitions." Tools are dict entries — the LLM is told about them in the system prompt, and Python dispatches on the string name.

teams/trip_agents/orchestrator/tools.py
TOOL_REGISTRY: dict[str, Callable[[ToolContext, dict], Any]] = {
    "search_flights":       search_flights,
    "search_hotels":        search_hotels,
    "search_cars":          search_cars,
    "get_user_preferences": get_user_preferences,
    "get_reservation":      get_reservation,
}

def search_flights(ctx: ToolContext, args: dict) -> list[dict]:
    filters = _clean_flight_filters(args)              # allow-list validation
    results = _run_search_graph(build_flight_graph,    # invoke sub-agent
                                filters, ctx.query)
    _publish_partial(ctx.thread_id, "flights", results)  # stream to UI
    return results

Three things are worth noting:

  • Filter sanitisation. The LLM might invent fields. shared/filters.py keeps only the allow-listed keys for each collection — the model can't smuggle a $where into your Mongo query.
  • Partial streaming. Each tool writes its results into trip_search_progress keyed by thread_id; the UI polls that document so flights, hotels, and cars appear in the left panel as they finish, not all at once.
  • Parallelism. Multiple search tools in one plan fan out via ThreadPoolExecutor (see below).
Independent search tools fan out in parallel; each merges back into the shared search_results dict.

06 Deep dive: the specialist sub-agents

Three almost-identical mini-agents. Each is two nodes: embed → vector search.

Every domain (flights, hotels, cars) is its own tiny LangGraph compiled from a shared builder. The same pipeline, parameterised by which MongoDB collection to query:

The shape of every search sub-agent.

One file is almost the whole agent

teams/trip_agents/agent_flight/agent.py (whole file)
from agent_flight.state import FlightSearchState
from shared.atlas import get_flights
from shared.nodes.search_nodes import make_embed_node, make_vector_search_node
from shared.search_graph import build_embed_search_graph

_embed  = make_embed_node("flight")
_search = make_vector_search_node(
    get_flights, "flight", "trip_flights",
    format_hit=lambda _i, r: f"{r['airline']} {r['flight_number']} — EUR{r['price_eur']}",
)

    return build_embed_search_graph(FlightSearchState, _embed, _search, "search_flights")

That's it. The interesting code lives in the shared factories — make_embed_node and make_vector_search_node in shared/nodes/search_nodes.py — so flight, hotel, and car logic stays identical and bug fixes happen once.

The vector-search node, in essence

def make_vector_search_node(collection_getter, label, collection_name, format_hit=None):
    def search(state):
        embedding = state["query_embedding"]
        filters   = state.get("filters", {})
        results   = vector_search(collection_getter(), embedding,
                                  limit=3, filters=filters)
        return {"results": results, "status": "complete"}
    return search

Inside vector_search() the actual MongoDB pipeline looks like this:

pipeline = [
    {"$vectorSearch": {
        "index":        "vector_index",
        "path":         "embedded_description",
        "queryVector":  embedding,           # 512 floats from Voyage
        "numCandidates": 100,
        "limit":         3,
        "filter":        filters,            # {city: "Amsterdam", stars: {$gte: 4}}
    }},
    {"$project": { "embedded_description": 0,
                  "score": {"$meta": "vectorSearchScore"} }},
]
results = list(collection.aggregate(pipeline))

Each collection has its own allow-list of filter fields — sanity defaults for the architect:

CollectionFilterable fieldsWhy
trip_flightsorigin_city, destination_city, travel_classOrigin/destination are exact-match constraints — semantic search can't be trusted for "Tokyo vs Toronto."
trip_hotelscity, stars ($gte)City must match; stars is an inequality, allowing room for upgrades.
trip_carspickup_city, make, category, color, transmission, fuel_typeMore structured filters available — vector search refines within the slot.

07 Deep dive: memory

LLMs are stateless. Anything you want the agent to "remember" you have to fetch and put back into the prompt.

Two storage strategies in two MongoDB collections; both flow back into the plan prompt at the start of every turn.

Short-term: replay the last few messages

Before each plan call, the orchestrator pulls the last 8 messages from trip_chatPersistence and formats them as plain text in the user prompt: 

Conversation so far:
  USER: Find me a flight to Tokyo next month
  ASSISTANT: Sure — economy or business?
  USER: Business please

Latest user message: "And add a 4-star hotel near Shinjuku"

Return JSON only:

That's how the LLM "knows" the city is Tokyo and the class is business when answering the new turn — not through any internal memory, just because we put it back in the prompt.

Long-term: extract preferences in the background

After every assistant turn, persist_and_learn spawns a background thread that runs a separate LLM call (memory_extraction.txt) over the new dialogue. If the model finds a durable preference — "prefers business class", "avoids diesel cars" — it's upserted into trip_longMemory, capped at 30 entries per agent.

On the next turn, load_preferences() reads those facts and appends them to the system prompt: 

User preferences:
- Prefers business class on long-haul flights
- Avoids diesel rental cars
- Likes hotels with a bar and river view

The user-visible effect: the agent gets better at the user's quirks over many sessions without you ever fine-tuning a model.

08 Modes beyond chat

A single subprocess entry point handles six operations, switched by AGENT_ARGS.mode.

The API picks the mode before spawning the orchestrator, using simple regex + keyword heuristics (_detect_message_mode in agent_platform/api/routes/trip.py):

ModeHow it's triggeredWhat the orchestrator does
chatDefault — any normal messageFull plan-and-execute graph (the one diagrammed above).
searchStateless "Run" modal, no chat threadSame graph, but skips chat persistence.
reserveUI sends a magic prefix __RESERVE__{json} when the user confirms a bundleSingle-node reserve graph — assigns TRIP-YYYYMMDD-XXXX, computes total, writes to trip_reservations.
cancelMessage contains TRIP-… + a cancel keywordLooks up + deletes the reservation document, writes a confirmation chat message.
modifyMessage contains TRIP-… + a change keywordPlan-and-execute in modify mode — searches only one category and stores results as "replacement candidates."
updateUI sends __UPDATE__{json} after the user picks a replacement cardPatches the reservation document with the new item and re-computes the total.
Why this isn't just one big mode. Confirming a reservation and cancelling one are deterministic database operations — no LLM should be in that loop. Putting them in separate "single-node graphs" reuses LangGraph state plumbing without paying the cost of a plan/synthesize round trip. The LLM only intervenes when the work is genuinely linguistic (parsing a search request, picking the best bundle).

09 Worked walkthrough

User types: "Plan a full trip to Amsterdam — flight, hotel and car". Here is every step, in order.

  1. t = 0 ms
    Browser → API
    trip_planner.html POSTs to /api/trip/{agent_id}/threads/{tid}/messages with { "message": "Plan a full trip to Amsterdam — flight, hotel and car" }. The user message is appended to trip_chatPersistence immediately so it's visible in the thread.
  2. t ≈ 20 ms
    API decides the mode
    _detect_message_mode checks for magic prefixes (none), then for a reservation ID + cancel/modify keywords (none), so mode = "chat". The route spawns an orchestrator subprocess with AGENT_ARGS JSON containing mode, thread_id, message, and the recent chat_history.
  3. t ≈ 0.6 s
    plan node — LLM call #1
    The orchestrator loads long-term prefs ("prefers business class"), assembles the system prompt from trip_planner_plan.txt, and calls llm.invoke(). The LLM returns: 
    {
  "intent": "search",
  "tool_calls": [
    { "tool": "get_user_preferences", "args": {} },
    { "tool": "search_flights",       "args": { "destination_city": "Amsterdam", "travel_class": "business" } },
    { "tool": "search_hotels",        "args": { "city": "Amsterdam" } },
    { "tool": "search_cars",          "args": { "pickup_city": "Amsterdam" } }
  ]
}
    Notice the long-term preference quietly raised travel_class to business.
  4. t ≈ 0.7 s
    execute_tools — fan out
    execute_tool_calls() runs get_user_preferences synchronously (cheap, no I/O), then submits search_flights, search_hotels, search_cars to a ThreadPoolExecutor(max_workers=3). Each runs its own compiled sub-agent graph.
  5. t ≈ 0.9 s
    3 × Voyage embed in parallel
    Each sub-agent's embed_query node calls Voyage AI with the user's full sentence — same text, three calls, since the embedding cache is per-agent. Each returns a 512-float vector.
  6. t ≈ 1.2 s
    3 × MongoDB $vectorSearch
    Each sub-agent runs vector_search() against its collection — flights → trip_flights, hotels → trip_hotels, cars → trip_cars — with the filters from the plan and a per-collection allow-list. Each returns the top 3 hits with a similarity score.
  7. t ≈ 1.3 s (streaming)
    Partial results published to the UI
    As each sub-agent finishes, _publish_partial upserts its results into the trip_search_progress document keyed by thread_id. The browser is polling GET /threads/{tid}/search-progress every second and renders cards in the left panel as they arrive. If Voyage is slow but Mongo is fast, hotels might land before flights — that's fine, the UI doesn't care about order.
  8. t ≈ 2.0 s
    synthesize node — LLM call #2

    What gets sent. Two strings are handed to the LLM — a system message and a user message. The orchestrator assembles both inside synthesize_node:

    1. System message — the trip_planner_synthesize.txt prompt, optionally followed by the agent's long-term preferences (from trip_longMemory, the same ones the plan node also injected):

    You are a trip booking assistant synthesizing search results for the user.

Given the user's request, tool results, and optional user preferences,
return ONLY a JSON object:

{
  "content": "Natural conversational summary for the user (2-4 sentences)",
  "search_results": { "flights": [...], "hotels": [...], "cars": [...] },
  "proposed_bundle": {
    "flight": {...} | null,
    "hotel":  {...} | null,
    "car":    {...} | null,
    "rationale":      "Why this combination fits the user",
    "total_cost_eur": 0
  }
}

Rules:
1. Include in search_results ALL options returned by tools.
2. proposed_bundle picks your best recommendation — null for empty categories.
3. total_cost_eur = flight + hotel*7 + car*7 (7 nights/days if unknown).
4. Never say the booking is confirmed.
5. If no results at all, set proposed_bundle to null.
6. Reference user preferences when a result matches them.

--- (appended only if long-term memory exists) ---
User preferences:
- Prefers business class on long-haul flights
- Avoids diesel rental cars
- Likes hotels with a bar and river view

    2. User message — the literal user query plus a JSON dump of everything the search step produced, capped at 6,000 characters. The payload is built like this:

    payload = {
  "user_query": "Plan a full trip to Amsterdam — flight, hotel and car",
  "search_results": {                       # full docs from each sub-agent
    "flights": [ {"airline": "KLM", "flight_number": "KL1234",
                  "origin_city": "Doha", "destination_city": "Amsterdam",
                  "travel_class": "business", "price_eur": 540,
                  "score": 0.91}, /* +2 more */ ],
    "hotels":  [ {"name": "Hotel Pulitzer", "city": "Amsterdam", "stars": 4,
                  "price_per_night_eur": 220, "score": 0.88}, /* +2 */ ],
    "cars":    [ {"make": "Volkswagen", "model": "Polo", "transmission": "manual",
                  "price_per_day_eur": 42, "score": 0.84}, /* +2 */ ]
  },
  "tool_results_summary": [           # compact recap — which tools ran, how many hits
    { "tool": "search_flights", "count": 3 },
    { "tool": "search_hotels",  "count": 3 },
    { "tool": "search_cars",    "count": 3 }
  ]
  # In modify mode three extra fields are added:
  #   "modify_mode": True, "reservation_id": "TRIP-...", "category": "hotel"
}

prompt = f"User request: {query}\n\nData:\n{json.dumps(payload)[:6000]}\n\nReturn JSON only."

    Why this shape. Three deliberate choices:

    • Full docs in search_results — so the model can quote real airline names, hotel names, and prices instead of inventing them.
    • Tiny tool_results_summary — gives the model a quick at-a-glance "how many of each did I get" without making it re-count arrays.
    • 6,000-character cap — guards against blowing the context window if a category returned unusually long descriptions; top results are kept since arrays are already trimmed to 3 by each sub-agent.

    What comes back. The model returns a single JSON object — parsed by shared.json_utils.extract_json — with two fields the orchestrator cares about (content and proposed_bundle):

    {
  "content": "I found a great Amsterdam package. The KLM 6 AM business flight is the cheapest non-stop; the Hotel Pulitzer is a quiet 4★ near the canals; and a manual Volkswagen Polo covers the city. Total around €842.",
  "proposed_bundle": {
    "flight": { "airline": "KLM", "flight_number": "KL1234", "price_eur": 540 },
    "hotel":  { "name": "Hotel Pulitzer", "stars": 4, "price_per_night_eur": 220 },
    "car":    { "make": "Volkswagen", "model": "Polo", "transmission": "manual", "price_per_day_eur": 42 },
    "rationale":    "Best price · matches business + city preference.",
    "total_cost_eur": 842.0
  }
}

    Where each output lands in the UI. content becomes the assistant's chat bubble on the right; proposed_bundle is rendered on the left as the "Agent's Recommended Trip" card with the Confirm Booking / Search Alternatives buttons. If the LLM call fails or returns malformed JSON, a deterministic fallback in synthesize_node assembles a bundle from the top hit of each category — the user never sees a blank reply.

  9. t ≈ 2.1 s
    persist + spawn memory thread
    The assistant message — text reply, search results, and the proposed bundle — is appended to trip_chatPersistence. A daemon thread is started that calls the LLM one more time over the new dialogue to extract any new preference facts and upsert them into trip_longMemory. This is fire-and-forget; the user response does not wait for it.
  10. t ≈ 2.1 s
    Subprocess prints the JSON envelope, exits
    Final line on stdout: __RESULT_JSON__:{...}. The API parses that line, marks the run as complete, and the browser — which was polling thread state — renders the assistant message and the bundle's "Confirm reservation" button.
  11. t = user clicks Confirm
    Reserve mode
    The UI POSTs __RESERVE__{...} as the next message. The API spawns the orchestrator again with mode=reserve; it runs the single-node reserve graph, mints TRIP-20260525-7K9F, and inserts the reservation document. No LLM involved — pure database write.
Cost & latency, at a glance. Two LLM calls per chat turn (plan + synthesize), plus one in the background for memory. The fan-out keeps end-to-end wall time near max(embed + vector search), not the sum. Each turn is a fresh subprocess, so a stuck LLM provider can never lock up the platform.

10 Glossary & source map

A pocket reference for terms used in this document and where to find the corresponding code.

Cheat sheet

Agent
An LLM wrapped in a loop that can call tools.
Tool
A named function the agent can request by emitting JSON.
Plan-and-Execute
LLM emits a full plan once; Python runs it; LLM writes the answer.
Orchestrator
The agent that sequences other agents.
Sub-agent
A small specialist agent the orchestrator delegates to.
LangGraph
A library for building stateful node-and-edge agent graphs.
Embedding
A vector representation of text used for similarity search.
$vectorSearch
MongoDB Atlas aggregation stage that finds the closest vectors.
Short-term memory
Recent dialogue replayed into the prompt.
Long-term memory
Extracted user facts stored across sessions.
ReAct
Alternative loop: one tool call at a time, decided iteratively.
Subprocess-per-turn
A fresh Python process handles each chat message — crash isolation, no shared state.
